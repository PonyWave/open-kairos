# 整体架构

本文描述 open-kairos 的当前架构。术语定义见[目标与范围](goals-and-scope.md)。

## 1. 启动与进程结构

`kairos start` 在一个命令中拉起 Server 与内嵌 Daemon。Daemon 通过 loopback WSS 连接本机 Server，配对、Operation 与输出回传和远程设备使用同一套协议。Server 在同一端口托管本地网页（GUI），启动时自动探测空闲端口并打印带本地会话令牌的访问地址；`KAIROS_PORT` 用于固定端口。

```text
kairos start
  ├─ Server（Fastify + SQLite + Agent Loop + Provider + 工具调度，同端口托管 GUI 静态页面）
  └─ 内嵌 Daemon（loopback WSS，执行主环境操作）
```

远程设备通过既有 Daemon 配对流程接入，协议相同。

## 2. 主环境与设备

Server 首次启动时自动注册主环境：写入环境记录、完成设备绑定，根目录默认为启动命令所在目录，可通过配置修改。主环境不可删除、不可撤销，默认出现在设备列表，模型侧别名为 `main`。

其他设备通过 Daemon 主动建立的 WSS 连接配对，设备身份、绑定与撤销机制对各设备一致。

环境之间的文件与目录复制由 `env_sync` 工具执行：在两个已授权环境之间复制普通文件或目录，冲突策略为 `fail`（默认值）、`skip` 或 `overwrite`，内容相同的文件始终跳过。同步意图、进度与结果保存在 `environment_operations` 命名空间。

`glob` 与 `grep` 工具经设备通道的 `FILE_SEARCH` 能力下发，Daemon spawn 内置的 ripgrep 15.0.0 子进程执行（随 Daemon 发布物打包并校验哈希与平台），输出行数与字节数有上限，超时中止。bash 工具的结果携带字节数有限的输出预览；完整输出超过预览时，Server 把流经自己的输出分块流式写入主机主环境工作目录的 `.kairos/logs/<operation_id>.log`（保留 7 天，单文件上限 64 MiB），结果 JSON 的 `output_file` 给出路径（`env_id` 固定 `main`）并附 `hint`，Agent 用 `read` 或 `grep` 以 `env_id=main` 继续读取。任何环境执行的 bash 日志都落在主机；Server 的 SQLite 输出分块只保留与预览一致的 16 KiB 头部，完整日志不进入 Server 数据库。

bash 工具的 `run_in_background` 参数把命令作为后台任务执行：Server 在 `background_tasks` 表登记后立即返回 `task_id`，操作经设备通道异步执行；终态结果先持久化，再绑定回复 Thread 的持久根 Run 直接注入模型输入，不创建普通 `follow_up`。`task_list`、`task_output`、`task_stop`、`task_wait` 管理后台任务（含 Subagent 任务），取代已移除的 `subagent_status` 与 `subagent_cancel`。

### 2.1 MCP 工具桥接

`KAIROS_MCP_CONFIG` 指定 MCP server 配置 JSON（`servers` 数组，`transport` 为 `stdio`（`command`/`args`/`env`）或 `http`/`sse`（`url`/`headers`））。每个 server 绑定一个环境：`env_id` 缺省为 `main`（主环境），也可填其他已授权设备的环境 UUID。Server 经设备通道在对应环境的 Daemon 上打开 MCP 会话并桥接工具，命名 `mcp__<server>__<tool>`：只在一个环境注册的 server 在工具描述中说明注册环境、不提供 `env_id` 参数；两个及以上环境同时注册的 server 在描述中列出环境，调用必须提供 `env_id`。

需要 OAuth 的远程 server 由 Daemon 上的认证流程宿主处理：工具列表返回 needs-auth 时，Server 合成 `mcp__<server>__authenticate` 工具，调用后经工具进度事件把授权 URL 推到 GUI（授权卡片带复制按钮），用户在浏览器完成授权，回调命中 Server 的 `/mcp/oauth/callback`；访问令牌与刷新令牌保存在 `mcp_oauth_credentials` 表，到期前自动刷新。

## 3. 工作空间与执行默认值

工作空间由名称、可选描述、`env_id` 和规范化工作目录组成，`(env_id, path)` 在租户内唯一。创建工作空间时在同一事务创建其工作空间 main。

- 执行规格按 Thread 所属工作空间记录默认 `env_id` 与路径，bash 等工具的默认执行位置为该目录。
- 工具的可选 `env_id` 参数：省略时使用工作空间默认值，显式传入时作为单次调用目标，可指向任何已授权设备和任意路径。工作空间不构成权限边界。
- 全局 main 与临时对话的默认执行位置为主环境及其根目录。
- 附件写入 `<工作目录>/.kairos/attachments/`。全局 main 与临时对话的附件写入主环境根目录下的 `.kairos/attachments/`。

### 3.1 资源快照

全部 Agent 的 `AGENTS.md` 与 `.agents/skills/<name>/SKILL.md` 资源快照固定从主环境 Daemon 用户的主目录读取（`~/.kairos/AGENTS.md` 与 `~/.agents/skills/<name>/SKILL.md`，主目录可用 Daemon 环境变量 `KAIROS_DEVICE_RESOURCES_HOME` 覆盖），保存在绑定历史快照中，与主环境工作目录无关，不随工作空间设备变化。

系统提示词按两级注入资源：`AGENTS.md` 注入全文；skills 注入目录（`<workspace-skills>`，每个 skill 一行名称与描述）。`SKILL.md` 支持 YAML frontmatter，`description` 字段作为目录描述；无 frontmatter 时描述回退为正文首个非空行，`name` 字段如存在必须与目录名一致。Agent 用 `skill` 工具按名称加载某个 skill 的完整正文，正文取自该执行固定的绑定快照，不经设备往返；读取 skill 引用的附属文件时用文件工具显式传 `env_id=main`。

`write` 与 `edit` 在目标环境执行成功后，Server 探测目标文件目录链上的 `AGENTS.md`（最多 5 级，主环境工作区根目录除外），发现时在工具结果中附加 `agents_md_hint` 提醒；同一执行内已提醒过的路径不再重复。需要精确当前时间时在 bash 中执行 `date`。

## 4. 对话层级与通知

| Thread 类型   | 数量           | 创建方式                                            |
| ------------- | -------------- | --------------------------------------------------- |
| 全局 main     | 每用户一个     | 系统初始化                                          |
| 工作空间 main | 每工作空间一个 | 创建工作空间时在同一事务创建                        |
| 任务 Thread   | 任意           | 全局 main 或本工作空间 main 通过 `thread_call` 创建 |
| 临时对话      | 任意           | 全局 main 通过 `thread_call` 创建                   |

- 全局 main 可调用任何 Thread，包括各工作空间 main。
- 工作空间 main 注册 `thread_call`、`thread_list`、`thread_read`、`thread_cancel`，范围限定本工作空间内的 Thread。
- 任务 Thread 与临时对话不注册 Thread 工具。

### 4.1 通知

- `thread_notify` 的目标参数：`workspace`（默认值，发送方所在工作空间的 main）或 `global`（全局 main）。
- 任务 Thread 只能通知本工作空间的 main 或全局 main，不能跨工作空间通知其他工作空间的 main。临时对话只能使用 `global`。
- 工作空间 main 注册 `thread_notify`，目标固定 `global`。
- 全局 main 向工作空间 main 发消息复用 `thread_call`，response 按委派三元组交付。

## 5. 召回与 Automation

- recall 只开放 `thread`、`context`、`recap` 三张查询表。`thread` 表包含 `workspace_id` 列，临时对话该列为 `NULL`。可见范围按调用方 Run 分级：全局 main 根 Run 覆盖本用户全部 Thread，工作空间 main 根 Run 覆盖本工作空间，其余限当前 Thread，矩阵见[数据定义与运行状态](domain-and-state.md#6-recall-查询表)。
- `workspace_list` 工具供 Agent 查询合法工作空间；`workspace_create` 工具供全局 main 创建工作空间（设备 + 工作目录，同一事务创建工作空间 main），工作空间 main 与任务 Thread 无权创建。
- Automation 定义包含可选 `workspace_id`。fire 创建新 Thread 时写入对应工作空间，为空时落入临时对话列表。
- 存储的触发时间带确定性 jitter：周期触发按 scheduleId 哈希延后至多 min(周期 × 10%, 15 分钟)，恰好落在整点或半点的 once 触发提前至多 90 秒；`automation_read` 展示实际触发时间。Server 停机期间错过的触发在恢复后合并为一次立即触发，投递的输入注明原定时间与合并次数。
- automation_only Thread 根 Run 的 recall 可见范围为本用户全部 Thread，dream 依赖该能力读取历史。
- 记忆目录存在时，根 Agent 的系统指令注入 Memory Wiki 索引（`MEMORY.md`，缺失或超限降级处理），全局 main 额外获得写策略；内置 `记忆整理 (dream)` Automation 按固定 client action 幂等播种，`new_automation_only` 目标每日触发，约定见[数据定义与运行状态](domain-and-state.md#8-memory-wiki-与-dream)。

## 6. IM 渠道

Server 内置渠道适配层，把微信与飞书接入全局 main。渠道凭证与绑定关系保存在 `channel_states` 表（凭证加密存储），入站去重记录在 `channel_inbound_events`，出站投递记录在 `channel_deliveries`。

### 6.1 入站

- 微信：腾讯微信团队维护的 ClawBot 通道（协议见 `Tencent/openclaw-weixin` 的 protocol 文档）。用户在设置页扫码绑定，Server 保存 `bot_token` 后以长轮询 `getupdates` 收消息；只接受绑定用户的私聊消息。绑定过程触发微信风控要求数字验证码（`need_verifycode`）时，设置页展示输入框，提交的 `verify_code` 随下一次状态轮询上报，验证码错误或锁定（`verify_code_blocked`）按协议重新输入或刷新二维码。入站消息入队后开启「正在输入」状态（`getconfig` 获取 `typing_ticket` 并缓存，每 5 秒刷新），该用户首条投递成功后取消；输入状态为尽力而为，接口失败不影响消息链路。
- 飞书：自建应用机器人，Server 使用官方 SDK 的长连接订阅 `im.message.receive_v1`，不需要公网入口。保存 App ID/Secret 后生成六位配对码，用户在飞书里把配对码发给机器人完成绑定。
- 入站消息追加到全局 main 的输入队列，`source` 为 `channel` 并携带 `channel` 引用（渠道、类型、外部消息 ID）；文本前注入 `<system-reminder>` 来源标记（注明渠道），GUI 气泡按引用显示渠道角标并隐藏该标记。平台消息 ID 用于去重；入站图片、文件等媒体在 v1 降级为占位文本。

### 6.2 出站与投递失败

- `send_to_user` 始终投递 GUI；全局 main 可额外传 `channels`（`wechat`/`feishu`）。工具执行时为每个渠道创建 `channel_deliveries` 记录，投递 worker 在事务外渲染并调用平台接口：微信渲染为纯文本分段（约 1500 字节），飞书渲染为卡片 JSON 2.0（`markdown` 组件，表格转原生 `table` 组件，单卡不超过 5 个表格、约 24 KB，超出拆卡，失败时降级纯文本）。
- 投递失败先按 2s/10s/30s 退避重试（最多 4 次尝试）；可重试错误耗尽或非可重试错误（未登录、登录态失效、权限不足）置为 `failed`，并向全局 main 注入一条 `channel` 来源、以 `<system-reminder>` 包裹的投递失败通知，内容包含失败原因、尝试次数、原内容与引导：可重试错误引导模型用 `send_to_user` 的 `redeliver_of` 重投（不产生新气泡），非可重试错误引导模型提示用户在设置页处理。
- 微信发送依赖入站消息携带的 `context_token`，长时间无入站时主动推送可能失败，按投递失败流程处理。

### 6.3 GUI

- 设置页「渠道」按微信、飞书分别展示品牌图标、状态、当前配对步骤和操作；桌面卡片保留内边距，手机表单使用 16px 输入字号和至少 44px 操作高度。密钥默认遮蔽，未保存凭据离开前提示，移除配置或解绑前确认。
- 微信登录会话在 Server 进程内保留，返回渠道页后可恢复当前二维码与验证码步骤。二维码过期或验证码锁定后刷新内容并同步 GUI；重新生成、取消、解绑和关闭服务都会撤销旧会话，旧结果不能改写当前账号。会话最长保留 10 分钟，验证码等待最长 5 分钟；进程重启后需要重新扫码。
- 微信查询中断与终态失败分别显示，自动状态刷新保留操作错误。手机页面说明可借助另一台设备展示二维码；本轮不承诺手机相册识码。
- 飞书保存凭据后进入配对码步骤，提供复制与状态查询；等待时自动查询，绑定成功后切换为账号摘要。已配置连接出错时可重新连接、修改凭据或移除配置；重新连接保留凭据与已绑定用户，收到连接就绪事件后再显示已连接。
- 每个渠道独立显示操作进度。凭据只在表单内存中暂存，不写入浏览器本地存储。已保存的 App Secret 不回显；同一 App ID 修改时可以留空保留密钥，更换 App ID 必须提供新的密钥。
- 本地品牌资源的来源记录在 `apps/gui/src/assets/channel-brands.md`。
- 入站渠道消息渲染为平台配色的用户气泡（微信绿、飞书蓝），平台图标角标位于气泡右上角（气泡靠右对齐的外侧一角）；投递失败通知渲染为系统通知卡片；`redeliver_of` 重投不产生新气泡。
- `send_to_user` 成功结果在精简视图与完整视图中均渲染为不折叠的气泡卡片，不再计入普通工具调用分组；完整视图在气泡内左上角展示「回复用户」胶囊（仅边框、无底色）。
- 携带 `channels` 的 `send_to_user` 气泡展示投递角标：投递中半透明、成功后实色；失败的渠道在角标旁显示「i」标记，悬停查看失败原因（错误详情不直接展示给用户，Agent 通过投递失败通知感知）。气泡的投递状态经 `ListChannelDeliveries` 批量查询并轮询至终态。

## 7. GUI 结构

- 侧栏按工作空间聚类：全局 main 固定顶部；每个工作空间分组显示名称、设备与路径，组内固定展示其 main 对话（无消息也展示）和任务 Thread；临时对话列表独立展示，不含 main 对话，没有临时对话时不展示该分组。
- 新建话题入口挂在工作空间分组内。
- 侧栏的“添加工作空间”直接打开创建窗口，“查看全部工作空间”进入独立地址 `?view=workspaces`。全部工作空间按组显示普通话题数量，默认收起为紧凑的单行卡片；收起时设备和目录缩为卡片顶部的一行面包屑，路径按可用宽度省略（最长占行宽一半），不重复展示主对话数量。工作空间卡片在展开时作为表头，描述、“新建话题”跟随其后，主对话与每个话题都以「全部对话」页的话题卡片样式单独展示（标题、时间与最近回复预览），卡片数据经 `ListThreadCards` 的 `thread_ids` 过滤按组加载。没有临时对话时该分组不展示。列表整条悬停高亮，操作图标在该背景上加强高亮。
- 每个工作空间支持编辑名称与描述、切换侧栏可见性及删除。隐藏只影响侧栏，全部工作空间仍列出；临时对话分组随列表有无自动展示，不提供隐藏开关。
- 工作空间主对话顶部提供“编辑空间”：设备与工作目录以创建窗口同款的一行展示（设备为小下拉样式、目录为输入框样式），均不可修改；「在侧边栏显示」为开关，切换即生效；编辑名称与描述保存后同步到该空间的主对话。
- 删除需要输入空间名称确认。服务端在事务内删除该空间及所属全部 Thread 的消息、执行与关联记录，不访问设备文件系统。存在执行中任务或仍引用该空间／其中对话的定时任务时拒绝删除；用户需先停止执行、修改定时任务的目标或删除定时任务。
- 创建窗口复用目录浏览 RPC，设备切换时使用该设备的推荐目录；空目录保留上级入口，支持分页浏览。设备为工作目录左侧的小型下拉，使用统一下拉组件；目录预览经输入框右侧的箭头展开或收起，预览区域高度固定，内容超出时区域内部滚动，不随子目录数量改变。展开时弹窗由中心向上、下两侧动画扩展，收起时动画恢复。
- 新话题的地址携带工作空间 ID，草稿按空间分别保存，刷新后保持归属。
- 任务 Thread 与工作空间 main 中经 `thread_call` 送入的消息渲染为左对齐的用户气泡，并展示发送方头像与来源标注：来自全局 main 时展示主对话头像、标注「来自主对话」；来自工作空间 main 时展示该主对话头像、标注「来自工作空间主对话」。
- 查看话题在右侧边栏打开话题对话，左侧保留当前对话：从全局 main、工作空间 main 或任务 Thread 打开时不切换左侧内容；从新话题草稿页或定时任务历史打开时回到全局 main 显示。
- 话题标题栏的定位入口跳转到发起该话题的对话并高亮原始委派消息：来源为全局 main 时回到全局 main，来源为工作空间 main 或任务 Thread 时全屏打开该对话；手动新建的话题没有该入口。
- 1020px 及以下使用顶部导航栏与侧边栏抽屉；导航按钮与正文分开布局，打开抽屉时限制键盘焦点在其中。
- 弹窗打开后 Tab 与 Shift+Tab 的焦点在弹窗内控件间循环，焦点控件显示描边高亮；标记初始焦点的控件（如破坏性确认的「取消」）在打开时获得焦点。
- 操作图标使用统一 SVG 组件：常规尺寸 16px、辅助尺寸 14px、大尺寸 24px，描边为 24×24 坐标中的 1.5 单位。点击区域按控件规定，工作空间列表和侧栏的触摸操作图标保持至少 44px 的点击区域。工作空间和对话的身份徽标保留独立造型。
- 全部对话卡片按工作空间分组。

### 7.1 界面动效（当前行为）

动效使用统一时长与缓动曲线：操作反馈为 120–180ms，页面与弹窗入场为 260ms，分组展开与收起为 240ms。样式集中在 `apps/gui/src/motion.css`，不依赖额外动画库。

- 页面与设置内容淡入，页面标题轻微上移；工作空间、话题、设备与定时任务列表依次呈现，延迟最高 96ms。鼠标悬停话题卡片时轻微抬升，按钮按下时缩小，输入框聚焦时显示边框与阴影反馈。
- 对话切换立即请求消息；加载超过 180ms 后显示低对比度骨架占位，消息就绪后立即淡入，不延迟实际内容。首次历史列表的整体入场与后续单条新消息的淡入分别执行。
- 导航与操作图标按用途提供悬停反馈：主对话图标轻微转动与缩放，定时任务时针轻摆，话题图标横移，设置图标转动，创建、编辑和关闭图标分别回应操作；工作空间徽标与账户头像提供小幅缩放。支持悬停的鼠标设备启用这些效果，键盘聚焦也提供图标反馈。
- 话题侧栏从右侧进入；窄屏导航抽屉平滑展开和收起，遮罩同步淡入淡出。关闭抽屉后立即禁止其内部控件获取焦点。
- 下拉菜单按实际弹出方向展开，视口边缘翻转方向后仍保持对齐。原生弹窗与背景遮罩淡入，弹窗本身不使用位移或缩放，保证内部下拉菜单的位置稳定。
- 工作空间与临时对话分组支持高度过渡。收起时立即移除其键盘与辅助技术访问，动画结束后卸载内容；快速切换展开状态时从当前位置继续过渡。
- 跟随对话底部时，新增消息使用 220ms 淡入。首次载入、加载历史、切换展示模式、隐藏对话，以及阅读较早消息时不触发新消息动效；同一条流式消息更新时不重复触发。消息动效只修改透明度，保留滚动定位所使用的几何尺寸。
- 系统启用“减少动态效果”后，关闭页面、列表、菜单、抽屉、状态指示及拖动归位动画，保留颜色、焦点与文字反馈；正在执行的新消息动效也会立即取消。
